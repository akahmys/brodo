# Architecture

The design as it is now. Why each part is this shape is in [docs/adr/](docs/adr/README.md);
a change to it goes through an ADR first (PLANNING.md §2). What is checked of it is in
[TESTING.md](TESTING.md) §1; what is still open is in [ROADMAP.md](ROADMAP.md) §3.

## 1. Purpose and scope

brodo holds, edits and stores sparse volumes in three dimensions (signed distance fields,
fluid fields, smoke, temperature) in pure Rust (ADR-0012). It is a part published on its
own and knows nothing of its users.

| User | Use | What it needs from brodo |
| :--- | :--- | :--- |
| a CFD solver | time-stepping fields, stencils | shared topology, neighbour tables, double buffering, leaf-parallel writes, determinism |
| a shape kernel | building, combining and offsetting level sets | tiles, random access, dilation and pruning |
| a process exchanging fields | passing grids between processes | a zero-copy, memory-mappable file |
| `colino` | converting and checking outside shapes | flood fill, connected components, Euler characteristic |
| a producer of Hermite data, such as one building from analytic shapes, and a reader building cut cells | writing and reading signs and edge crossings without knowing each other | the Hermite data format (§4.9) |
| a developer or agent checking a change | seeing a field | a slice as PNG, a field for ParaView (§6.1) |
| a process inspecting grids | viewing a grid file as an external program | `piatto`'s program, if built (§6.2) |
| an application with its own interface | showing grids inside it | `piatto`'s drawing library, if built (§6.2) |

**Out of scope**: level-set operations (CSG, offset, redistancing) and SDF-to-mesh; solvers,
discretisation and linear algebra; an application's own interface (choosing faces,
labelling, showing provenance), which belongs to the application (ADR-0018).

Two-dimensional fields are kept on a grid one leaf thick: a leaf of 8³ is fixed
(ADR-0013), so a field one voxel thick in z still takes a leaf's eight layers. brodo has
no two-dimensional mode and is not expected to gain one (ADR-0012). An axisymmetric run is
a discretisation, its user's.

## 4. `brodo`

### 4.1 The tree (ADR-0013)

- Four levels: a root `BTreeMap` keyed by coordinate → internal nodes of 32³ → internal
  nodes of 16³ → leaves of 8³ (512 voxels).
- Each node marks its children and tiles by bit masks; offsets come from `count_ones` and
  `trailing_zeros`.
- A **tile** stands for a uniform region in a child's place, without a leaf. The
  **background** is the value outside the tree.
- A leaf holds no per-voxel active state: all 512 voxels are active (ADR-0025).
- Activating a voxel creates its leaf, and the nodes above it, where none is; inside a
  tile it changes nothing. Splitting a tile turns each level on the path to the voxel into
  a node whose other children are tiles, down to one leaf.
- Nodes live in one arena (`Vec`) per kind, referred to by `u32` index. The concrete node
  types are generated by a macro.
- Voxel coordinates are three `i32`. The world transform (voxel size and affine map) is
  grid metadata.

### 4.2 Topology and fields (ADR-0014)

```rust
pub struct Topology { /* the tree, its stamp, its leaves and tiles numbered */ }
pub struct Field<T> {
    leaf_values: Vec<T>,   // leaf count × 512, outside the leaves
    tile_values: Vec<T>,   // one per tile
    background: T,
}
```

- Where a tile is belongs to the topology; its value belongs to each field.
- A topology numbers its leaves and its tiles in the Morton order of their origins, rebuilt
  at each `commit`; tiles never share an origin, so the order is total. Leaf numbers, and
  so the order of field values, follow it. A voxel is located through the tree, then
  numbered. `Topology::leaf_voxels` gives a leaf's voxel coordinates in the order of its
  values, x fastest, then y, then z; `TileLevel::edge` a tile's edge in voxels.
- `Grid<T>` binds one `Topology` and one `Field<T>` for single-field use, with the merge
  rule chosen when it is made (the same-bits rule unless another is given). Its `edit`
  takes the edits as a closure, commits them and remaps the field in one step; if any part
  fails, the grid is unchanged. Its field is written through the grid (`par_update_leaves`,
  `leaf_mut`, `set_tile`), never handed out to be replaced, so that it is always the
  topology's (ADR-0014).
- Topology changes (activation, removing a leaf, dilation, pruning, splitting and merging
  tiles) go through an editor (`TopologyEditor`) and take effect at `commit`, which
  returns a new topology and a `Remap` to it, and leaves the old topology usable. Every
  field on the old topology is remapped by it. Removing a leaf removes the nodes it leaves
  empty; in a tile it is refused (ADR-0025). Every tile in a region becomes leaves by one
  `split_tile` per leaf origin in it that a tile holds, in one editor, so one `Remap`; there
  is no operation of its own until a benchmark shows the calls cost (ROADMAP.md §4, R8).
- Every topology carries a stamp unique in the process. A field records the stamp of the
  topology it was made or remapped for; using it with another topology, a remap included,
  is the typed error `StaleField`.
- `Remap` records, for each new leaf, where its values come from: an old leaf, the tile it
  was split from, or the background. For each new tile it records an old tile, the
  background, or the parts it merges: old leaves and old tiles, in one list for all merged
  tiles, each tile holding its range in it. A split leaf takes each field's own tile value.
  A region whose leaf the edit removed is the background to the commit: a leaf or tile the
  same edit puts there takes nothing of the removed values (ADR-0014).
- A merge takes leaves and tiles at once, into a tile in a lower node (from a leaf) or in
  an upper node (from a lower node); a region that holds nothing refuses it, so a merge
  changes values, not which voxels are active. Merging into a root tile is not built.
- An edit that removes a leaf or a node leaves its arena entry unreachable; `commit`
  rebuilds the tree's arenas from what the root reaches, so nothing unreachable outlives
  a commit.
- A merged tile's value comes from a merge rule given to each field's remap, which sees
  each value with the number of voxels holding it, `Fn(&[(T, u32)]) -> Option<T>`; `None`
  refuses the merge, and so the commit's remap, with a typed error. brodo provides the
  rule that accepts only values with the same bits. Rules run only for merged tiles that
  exist after the commit, in tile order, so the error does not depend on the thread
  count.
- Values are updated and the topology edited in separate phases; while values change, the
  topology is read-only.

### 4.3 Leaf manifest (ADR-0014)

`LeafManifest` is part of a topology, derived from its tree and rebuilt at each `commit`;
the tree is the only source of truth. It holds, in leaf-number order (§4.2), what lies one
leaf away from each leaf in each of the 26 directions: a leaf, a tile with its level, or
the background, as a `Location` (CODING.md Rule 5). Directions are numbered with x
fastest. A neighbour beyond the `i32` coordinate range is the background.

### 4.4 Access and parallel work (ADR-0015)

- `ValueAccessor` borrows `&Topology` and `&Field<T>` (or `&mut`), caches the last node
  path for nearby access, and is held one per thread. It serves reads beyond the
  neighbour table. Its field's stamp is checked once, when it is made. It writes only
  voxels of leaves; a write to a tile's or the background's voxel is a typed error naming
  what holds it, since values change while the topology is read-only (§4.2).
- Leaf-parallel work runs on `rayon`, in the caller's pool: the global one, or the one a
  caller's `ThreadPool::install` or `RAYON_NUM_THREADS` sets, so that it shares its threads
  with a caller's own parallel loops (ADR-0015). No `rayon` type appears in brodo's API.
- The leaf-parallel update reads the old field by `&` and writes the new field by
  `&mut`, one 512-value chunk per leaf. Its function may fail; the error returned is that of
  the lowest-numbered failing leaf.
- A gather copies a leaf and one ghost layer from its 26 neighbours into a dense 10³
  array, filling missing neighbours with tile or background values; `gather_wide` copies
  one, two or three layers (`GhostWidth`) into a caller's `Vec` of (8 + 2w)³ values. A
  read beyond the window goes through `ValueAccessor`, faster than `Field::value_at`
  there (ADR-0015). Several fields of a leaf are gathered one call each.
- Reductions have a fixed-order mode whose result does not depend on the thread count: a
  partial result per leaf, in parallel, folded in leaf order.

### 4.5 Topology analysis

- Connected-component labelling on the sparse tree, tiles included, with 6- or
  26-connectivity, of the voxels whose value meets a condition (`Fn(T) -> bool`), applied
  alike to leaf voxels, tiles and the background; no per-voxel mask is needed. Flood fill
  is the component of a seed, built on the labelling. Each component says whether it
  reaches the unbounded background outside the tree.
- The units joined are leaf voxels, tiles, the empty places of lower and upper nodes and
  of the root (each a region of its own size), and the outside. Empty regions at the root
  are found on a grid compressed along each axis around the root's keys, so enclosed
  background stays apart from the outside. Adjacency between regions of different sizes
  is found by descending the levels with an explicit stack, never voxel by voxel over a
  large region. Components are numbered in the order of their first unit, so labels do
  not depend on anything but the input.
- The Euler characteristic χ of the voxels meeting a condition (ADR-0024): of the closed
  unit cubes under 26-connectivity, of the open ones under 6. Each lattice vertex owns
  the cells on its positive side, so χ sums a table of its 2×2×2 pattern; a vertex
  touching a leaf is summed by the leaf holding the first of its voxels, per leaf in
  parallel; elsewhere only the edges of the tiles meeting the condition are walked. A set
  holding the background is unbounded and refused.
- Dilation and erosion (ADR-0025), by k steps, 6- or 26-connected. Of a topology, on
  whole leaves: dilating adds a leaf at every background cell within reach of a leaf or
  tile, eroding removes every leaf within reach of the background, splitting a larger
  tile where it must; each returns its `Remap`. Of values on a fixed topology: a max or a
  min over the neighbourhood, k times, written to leaf voxels only.

### 4.6 Frozen view (ADR-0016)

- `freeze()` packs tree and values into one contiguous byte buffer, read as
  `GridView<'a>` without copying, through `zerocopy`.
- The header places each section by its offset from the start, in 32-byte blocks; a link
  between nodes is a number within its section: a node's first child and first tile, the
  rest found from its masks. Every structure is 32-byte aligned, little-endian, and laid out
  in `u32` words.
- Layout version 1: a header, the root table, upper nodes, lower nodes, leaf values and
  tile values, in that order; its bytes are in [docs/formats.md](docs/formats.md) §2.
- A node's masks number its children's places in Morton order, so that its children,
  being consecutive in that order, are found as its first child's number plus the set bits
  below the place; no list of child numbers is stored. Tile values follow the same rule.
- A view is made only from a buffer it has checked whole: alignment, magic number,
  version, value type, every section within the buffer, and every node's children and
  tiles within their sections. It accepts the layout versions ADR-0038 keeps, version 1
  alone so far; any other is a typed error naming it.
- A view thaws into an owned `Topology` and `Field<T>` (`GridView::thaw`), or into a field
  on a topology holding its leaves and tiles (`thaw_on`), by walking its nodes once and
  refusing a node, a leaf or a tile value reached twice, and a leaf never reached; the
  topology numbers them in its
  own order, so that one buffer gives one topology. Views whose root tables, nodes and
  counts agree hold one tree (`same_topology`) (ADR-0042).

### 4.7 Files (ADR-0016)

| Profile | For | Content | Read by |
| :--- | :--- | :--- | :--- |
| **cache** | passing between processes, replaying frame caches | the `GridView` buffer, uncompressed | memory mapping, no copy |
| **archive** | storing, shipping | metadata, topology and value blocks in compressed chunks of hundreds to thousands of leaves | decompressing chunks, in parallel, into a `GridView` (one copy) |

- A cache file holds a header (magic number, format version, grid count) and, per grid, its
  name, value type, voxel size and unit, affine transform, bounding box and free
  key-value metadata, the topology and the values; a bare frozen buffer, a file of its own,
  holds one grid's header, topology and values (docs/formats.md §2).
- A grid's metadata is a `GridMeta`, apart from `Grid<T>`, so that any topology and field
  can be written: a name, a voxel size per axis, a unit, a 3×4 affine transform from voxel
  to world coordinates, and free string pairs. The unit is a non-empty UTF-8 string brodo
  does not interpret; the voxel size and unit are always present. The bounding box is
  worked out from the topology when a file is written; a grid with no leaf or tile has an
  empty one, a variant of its own.
- The cache profile, format version 1: a header, a directory, then each grid's metadata
  and frozen buffer (§4.6) on block boundaries; its bytes are in
  [docs/formats.md](docs/formats.md) §3. A reader checks the whole file, every grid's
  buffer included, before it answers: no gap between the parts, zero padding and unused
  words in the header, the directory and the metadata, nothing after the last grid, and
  each buffer as docs/formats.md §2.5 checks it, which leaves some of its writer's rules
  unchecked (ADR-0016, ADR-0038).
- A cache file is written whole: to a hidden file beside it, flushed and renamed over it,
  so that a reader, a mapping process among them, sees the old file or the new one; the
  directory must be writable, and a process killed while writing may leave the hidden
  file behind.
- A cache file is read by copying it into an aligned buffer (`CacheFile::read`) or by
  mapping it into memory without a copy (`CacheFile::map`); both go through one parser.
  Mapping is brodo's only unsafe code, in one module (ADR-0008); while a file is mapped,
  the caller keeps it unchanged.
- The archive can decompress only the chunks a region needs, and can quantise values
  (16-bit float, 8-bit range), byte-shuffled before compression.
- OpenVDB files (`.vdb`) are read through the `vdb-rs` crate into brodo's tree and written
  by brodo, for level sets and scalar density first.

### 4.8 Value types

A field holds any type implementing brodo's `Value` trait: `Copy`, `Send` and `Sync`, with
a comparison by bits for merge rules, and `zerocopy`'s traits, so that its values are plain
bytes. `Value` is open: a field, its parallel update, gathers, accessors and analyses take
a type of a user's own. Frozen grids and cache files hold only `Stored` types, a sealed
trait over `Value` that brodo implements for `f32`, `f64`, `u8`, `u32`, `[f32; 3]` and
`[f64; 3]`, each named by a type code brodo assigns, 1 to 6 in that order (ADR-0029).

### 4.9 Hermite data (ADR-0032)

A format any producer writes and any reader reads without knowing the producer: a sign at
each lattice point and, on each edge whose ends differ, where a surface crosses it, its
normal there and its group (Ju et al. 2002). The producer's methods are its own; colino's
are in ADR-0030.

- Lattice: point v at the corner of voxel v, the image of v under the grid's transform,
  the sampling lattice of an SDF on the same topology shifted by −h/2. Point v owns its
  +x, +y and +z edges.
- A set, `brodo::hermite::Hermite`, is ten fields on one topology: signs (`u8`, 1 inside,
  0 outside), and per axis a fraction (`f32`), a normal (`[f32; 3]`) and a group (`u32`),
  with a table naming each group, group 0 `""`.
- An edge has a crossing exactly when the stored signs of its ends differ, tiles' and the
  background's included; its owner is then a leaf point. The fraction is the crossing's
  place from the edge's lower end, in [0, 1]; the normal is of unit length within 1e-6,
  its component along the edge, where not zero, pointing from the inside end outward. An
  edge with no crossing, every tile and the background hold fraction −1, normal zero and
  group 0, by bits; the signs' background is 0.
- A set is checked whole when made and when read; a broken rule is a typed error naming
  the point, the axis and the rule. Of several broken rules, which is named is not
  promised.
- In a cache file, a set is ten grids told apart by keys in `GridMeta::extra`, the sign
  grid holding the group table ([docs/formats.md](docs/formats.md) §4). A reader reads a
  set as ten `GridView`s, without a copy, the shared topology checked by comparing their
  root tables and node sections and their counts of leaves and tiles, and the sign grid's
  nodes walked from its root table, each reached once and every leaf reached
  (docs/formats.md §4.2, rules 3 and 11).
- A producer's own information, such as edges it found no surface for, is not in the
  format; it reports it beside the set.

## 5. `colino` (ADR-0017)

### 5.1 Conversion

- Input: STL (binary and ASCII), OBJ, 3MF, in that order, each read into a `Mesh` of `f64`
  vertices, `u32` triangles, a group per triangle (ADR-0030) and the file's unit, if any,
  under limits its caller sets (ADR-0026). Badly oriented, holed and degenerate meshes are
  accepted as they are; `Mesh::welded` joins vertices at equal positions, never within a
  tolerance. A 3MF package is read through `rawzip`, `miniz_oxide` and `quick-xml`, its
  model as a stream; the mesh holds every build item placed by its transforms. STEP and
  other boundary representations are not read: a user working with B-reps triangulates
  with its own kernel and passes a `Mesh`, its faces' names as triangle groups (ADR-0030,
  ADR-0031).
- Grid: the caller's voxel size, on the world's lattice unless given another origin; each
  voxel sampled at its centre (ADR-0027).
- Distance: exact, to the nearest triangle through a BVH of axis-aligned boxes.
- Sign: inside where the generalised winding number is 1/2 or more, by Barill et al.'s
  far-field approximation (β = 2, second order) or the exact sum, by default; or, as an
  option that does not depend on orientation, where most of the three lines through the
  point along the axes cross the mesh an odd number of times, a line with an odd count not
  voting and a tie outside, a line exactly on an edge or a corner counted as if moved by
  (ε, ε²). A point on the mesh, at distance exactly 0, is inside whichever is asked for, as
  in Hermite data, and an inside voxel whose distance rounds to zero holds
  −`f32::MIN_POSITIVE`, so that `v < 0` finds it. The winding number holds where parts
  pass into each other or walls are doubled; parity holds where faces are turned, across
  small holes, and in cavities; within a missing cap's sag a line across finds nothing
  (ADR-0027).
- Output: leaves only in a band of ±N voxels around the surface (N = 3 by default), values
  signed distances clamped to ±N·h. A leaf-sized cell is a candidate when it overlaps a
  triangle's box grown by N voxels and its centre lies within (N + 4√3)·h of the triangle,
  its centre's distance to a corner being 4√3·h; it stays a leaf when one of its voxels
  lies within the band; negative tiles inside, each region classified once,
  from the root region down, by its centre's sign; the positive background outside. Beyond
  the band of an open mesh, where the inside is not defined, the boundary the signs give
  across a hole follows the regions, as coarse as the tiles there. No dense grid: memory follows
  the band's volume, at 3000³ resolution as well. These are brodo's SDF convention, version
  1, which the grid's `extra` names under the key `sdf.version` (`brodo::meta::SDF_KEY`,
  ADR-0039) so that any producer can claim it.
- Hermite data: a set in brodo's format (§4.9) on the conversion's topology, its signs
  found by the conversion's sign and its crossings found by a watertight edge test, with the count
  of crossed edges no triangle was hit on beside it, whose crossing is the nearest triangle's:
  of triangles whose distances to the edge are equal within their rounding, which is taken
  is not promised (ADR-0030).
- It reports changes; it does not repair a shape or refine a grid.

### 5.2 Topology report

| Layer | Content | Method |
| :--- | :--- | :--- |
| 1. Global invariants | β₀, β₁, β₂ of the solid (φ < 0) and of its complement (φ ≥ 0) in the 3-sphere | β₀: components; β₂: complement components not reaching the outside; β₁ = β₀ + β₂ − χ |
| 2. Labelled connectivity | whether user-labelled regions lie in one complement component | flood fill |
| 3. Local risk | places thinner, or gaps narrower, than two voxels | from the mesh: a ray along each sampled point's normal, both ways; places with their boxes |

- Connectivity: the solid 26, its complement 6. The complement's β₀ is counted and held
  by tests to duality with the solid's β₂; its β₁ and β₂ are the solid's by duality, since
  under this pairing each lattice vertex adds as much to the complement's χ as to the
  solid's: β₁ the solid's, and β₂ the solid's components less one where there is a solid,
  and, by convention, 1 where there is none (ADR-0028).
- Reference for layer 1: the input's V − E + F when, welded, it is a closed 2-manifold,
  the solid's χ being half the surface's; otherwise none, the report saying why. Layer 3's
  check stands in for it where it is thin, for any input.
- Layer 2's regions are named points in world coordinates, each answered with its
  complement component, whether that reaches the outside, or the solid.
- Layer 3 samples points h/2 apart on every triangle and measures, along the triangle's
  normal both ways, the distance to the nearest other triangle: a side whose midpoint is
  inside by the conversion's sign is a wall that thick, otherwise a gap that wide. Points
  below 2h, of one kind and within 2h of each other, are one place, reported with its
  kind, its box, its least thickness or width and its count of points (ADR-0028). It
  samples, so a thin place between samples, or whose sides do not face along the normal,
  can be missed. Each place is checked in its box, grown by 2h and aligned to the voxels:
  the solid at h, the conversion's, and at h/2, the voxel centres the conversion's sign puts
  inside, compared by χ and by the solid's and the rest's components; differing, the
  conversion changed the topology there. A box of more than 2²⁶ voxels at h/2 is not
  checked, and says so (ADR-0028).
- The report is a structure serialisable with `serde` behind the feature `serde`: what may
  have changed, where it may lie (layer 3), and by how much.

## 6. Visualisation (ADR-0018)

### 6.1 Checking output

In `brodo`, each behind a cargo feature:

- **A slice as PNG** (`brodo::slice`, feature `slice-png`, opted into, ADR-0036), along x, y or z
  at a given position, one voxel to a pixel. Signed distances take a diverging colour map
  centred on zero, with the zero contour drawn one pixel wide; other scalars a sequential
  one. The colour range is given by the caller, never inferred, and refused unless it is
  finite and not empty. A tile's voxels take its
  value's colour, hatched; the background is a flat grey; a value that is not a number is
  magenta; with no per-voxel mask (ADR-0025), nothing else is inactive. The same input gives
  the same bytes. The encoder is `png`, pure Rust. The slices kept as golden images are
  written to `out/slices/` for a look by
  `cargo test -p brodo --test slice_images -- --ignored`.
- **A field for ParaView** (`brodo::vtk`, feature `vtk`, opted into, ADR-0036), written from the
  published file-format documentation only, as one ASCII UnstructuredGrid (`.vtu`): a
  VTK_VOXEL cell per leaf voxel, a tile one cell of its region's size, in index space,
  points shared and `Float64`, values as cell data (ADR-0018, B-012): a scalar field as
  `Scalars`, a field of `[f32; 3]` or `[f64; 3]` as three-component `Vectors`, one field
  per file. A NaN, or a NaN component, is written as `NaN`; an infinity is refused, since
  VTK reads `-inf` back as `+inf`. The same input
  gives the same bytes. The files read back in VTK are written to `out/vtk/brodo/` by
  `cargo test -p brodo --test vtk_reference -- --ignored`, and checked by
  `out/vtk-venv/bin/python -I spikes/vtk/check.py out/vtk/brodo`. Binary data waits for
  its header's documentation.

### 6.2 `piatto`

Not built until a user asks for a viewer or for drawing to embed, grids too large for VTK and `.vdb` must be looked at, or P6 finds `.vdb` cannot be written (ADR-0018); the slice as PNG and VTK serve meanwhile. The design
it would follow:

- Reads a cache-profile file (§4.7) by memory mapping.
- Its first version draws only: an isosurface by ray marching (zero by default); a slice,
  with its position moved by the user; a choice among the file's grids.
- Its drawing is a library that applications embed; its windowed program is a thin user
  of it. Window, input and GUI parts are chosen by B-013.
- It reads a `GridView` buffer on the GPU as it is (§4.6); what cannot be read there is
  recorded as a question on the frozen layout.
- Not in it: an application's own interface (§1), and fields' own kinds of drawing (stream
  lines and the like), for now.

## 7. Compatibility

- Before 1.0 the API may break; every break is in CHANGELOG.md (TESTING.md V3), and users
  pin a release tag; a user needing a change before its milestone gets a small release
  rather than a revision, so that crates sharing one process can agree on one tag
  (ADR-0040).
- The `GridView` layout and each file profile have their own format version (TESTING.md
  V6); a release reads its own and the one before it (ADR-0038).
